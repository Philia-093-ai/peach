## 5. 今天要掌握的问题（自答）

**防了哪一种重复提交或错误输入？** 三层，各防一种：

1. **格式层**：缺必填字段（scene / name）、名字超 20 字、请求体不是 JSON、请求体超 4 KB → 当场拒绝，回中文人话，数据根本进不了库。
2. **关联层**：场景名不存在 → 先查 `scenes` 表拿 `scene_id`，查不到就拒绝（否则写进去的名字会挂在空处，变成孤儿数据）。
3. **数据层（重复提交）**：同一场景下同一个名字写第二遍 → 数据库唯一约束 `names_scene_name_key` 拦下，函数把 `DATABASE_23505` 翻译成 **409** 中文。

**为什么重复要交给数据库拦，而不是函数里"先查有没有"？**
"先查再插"中间有时间差：两个请求同时来，都会查到"没有"，然后都插进去。
唯一约束是原子的——同一瞬间只可能有一个成功。Day 16 埋的那条 `UNIQUE (scene_id, name)` 今天兑现了价值。

**怎么测的**：本地 14 用例 + 公网 16 次请求（见第 2、3 节），每个拒绝分支都实际打了一遍，
且用「写前 36 行 → 写后 37 行 → 读回 count=7」闭环证明写入真实落库。

## 6. 余力加练：服务端日志

每次请求打一行结构化日志（云函数日志里可查）：

```
[peach-api][req] {"t":"2026-10-11T14:13:19.688Z","method":"POST","path":"/names","status":201,"ms":570,"ok":true,"note":"created id=76 (meaning truncated)"}
[peach-api][req] {"t":"2026-10-11T14:13:19.819Z","method":"POST","path":"/names","status":409,"ms":129,"ok":false,"note":"duplicate"}
[peach-api][req] {"t":"2026-10-11T14:13:19.975Z","method":"POST","path":"/names","status":400,"ms":0,"ok":false,"note":"missing scene"}
```

`method/path/status/ms/note` 齐了：出问题时一眼看出"哪个请求、多久、成没成、为什么"。
本地测试时 14 条日志与 14 个用例一一对应（见上，`note` 就是分支名）。
