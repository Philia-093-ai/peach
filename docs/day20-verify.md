## 2. 今天要掌握的：跨域问题是怎么认出来的（Day 17 复盘 + 今日复验）

**排查五步法**（第 3 步是"认出它"的关键一下）：

1. **看现象出现在哪一层**：Console 只有一句 `Failed to fetch`；Network 里那条请求是红色、状态 `net::ERR_FAILED`，**连响应头都看不到** —— 说明不是"服务器拒绝了"，而是"浏览器根本没让响应进门"。
2. **排除接口本身**：用 Python/curl 不经浏览器直接请求同一地址 → 200 + 正常 JSON。接口是好的，问题只能出在浏览器与服务器之间的那道"关卡"。
3. **模拟浏览器的身份再问一次**：请求时带上 `Origin` 头（浏览器跨域请求一定会带它），看响应头。Day 17 抓到的现行：
   ```
   access-control-allow-origin: https://xxx.tcloudbaseapp.com,*
   ```
   **两个值拼在一个头里 = 非法值**（这个头只允许一个值），浏览器见到直接丢弃整个响应——这就是 `Failed to fetch` 的真身。
4. **追问多出来的那个值哪来的**：CloudBase 网关会自动把 Origin 回显进这个头（第一层 CORS），函数里又手写了一个 `*`（第二层）→ 两层叠加打架。
5. **修法**：函数删光 CORS 头，跨域统一交给网关（Day 17 已修，此后一直健康）。

> 教训：**平台层已经做了的事，业务代码别做第二遍——两遍不是双保险，是互相打架。**

**今日复验**（开工探针，带 Origin 裸请求看响应头）：

| 请求 Origin | 响应 `Access-Control-Allow-Origin` | 判定 |
| --- | --- | --- |
| `https://…tcloudbaseapp.com`（静态托管页） | 同一个值（单一合法） | ✅ |
| `http://localhost:3000`（本地开发页） | `http://localhost:3000`（回显） | ✅ 本地页面也能直连公网接口 |

## 3. 首页「名字库实时数据」区（今天的前端改动）

- **数据从哪来**：`/api/health`（自检 + 服务端时间）+ `/api/scenes`（场景清单）+ 每个场景各一次 `/api/library?limit=1`（只取 `total`，即该场景库里到底有几个名字）→ 加总成 37。7 个请求**并发**发出（`Promise.all`），实测 0.4–5 秒。
- **交互**：场景标签可点，切换下面的名字预览（卡片和复制按钮完全复用 Day 8 的组件）。
- **检查台三行**（余力加练落点）：🛰 云函数自检（service + version）/ 🕘 数据最后更新（服务端时间）/ ⚡ 本次读取（请求数 + 耗时）。
- **四种状态照旧**（Day 8 心法）：加载 / 成功 / 空 / 错误（错误给人话 + 重试按钮）。

## 5. 改库跟着变（含今天新踩的一个坑）

| 步骤 | 操作 | 页面表现 |
| --- | --- | --- |
| 改前 | — | 浪屿 · 想象一座海上小岛，安静得只听得见浪。 |
| 改库 | `UPDATE names SET meaning='（Day 20 真库验证：这行文案刚在数据库里改过）' WHERE id=1`（Affected rows: 1） | — |
| 刷新 | `location.reload()` | 浪屿 · **（Day 20 真库验证：这行文案刚在数据库里改过）** ✅ 其余卡片不变 |
| 还原 | `UPDATE … SET meaning='想象一座海上小岛，安静得只听得见浪。' WHERE id=1` | 浪屿 · 想象一座海上小岛… ✅ |

**今天新踩的坑（自动化脚本侧，记下来免得再踩）**：第一轮用"navigate 到同一个 URL"来模拟刷新，因为地址里的 `#/gen` 没变，浏览器把它当成**同页跳转**，页面根本没重载、请求没重发 → 误报"没跟着变"。换 `location.reload()` 强制刷新后一切正常。人手动按 F5 不受影响；这是自动化验证的坑，不是产品 bug。
