## 1. 今天要掌握的：删除为什么更容易出事？确认加在哪？

**为什么**：新增一条数据，错了顶多是一条废数据，删掉就完事；**删除一条数据，错了用户的东西就没了**——
而且删错往往不是"点错按钮"这种大事，而是"脚本少写了个条件""地址栏手抖"这种小事。所以删除这条路，peach 设了**三道手续**：

| 道口 | 在哪 | 具体做法 | 防的是谁 |
| --- | --- | --- | --- |
| ① 服务端确认 | `DELETE /api/names/:id?confirm=<名字>` | 必须把"要删的那个名字"原样写一遍，和库里的**一字不差**；不带/写错 → 400 一条不删 | 脚本、curl 手滑、地址栏误改 |
| ② 前端两步确认 | 词库页「删除」按钮 | 第一次点**只变红**问「确认删除「xxx」？」，**一个请求都不发**；再点一次才真删；4 秒不点自动收回 | 误点、连点、点完就后悔 |
| ③ 默认软删除 | 数据库 `is_deleted` 标记 | 默认只翻标记（数据还在，restore 找回）；真删必须显式写 `?mode=hard` —— 把"不可逆"留给一个必须明说的入口 | 删完就后悔的人 |

> 一句话：**新增可以"发了就建"，删除必须"问过再删、删了还能反悔"。** 这三道不是过度设计——第 ②③ 道在今天的演示里真的用上了（见第 5 节）。

## 3. 新接口的约定（摘要，全文见契约第 6 节）

| 接口 | 成功 | 拒绝 |
| --- | --- | --- |
| `PATCH /api/names/:id` | 200，只改传的字段（name/meaning），改名字时 char_count 服务端重算 | 没有可改字段 400 / 名字空 400 / 超 20 字 400 / 编号非数字 400 / 撞同场景名 409 / 不存在（含已删）404 |
| `DELETE /api/names/:id?confirm=<名字>&mode=soft\|hard` | 200，回执带 `mode` 与 `recoverable` 和被删的那条 | 不带 confirm 400 / confirm 写错 400 / 不带编号 400 / 不存在（含已删）404 |
| `POST /api/names/:id/restore` | 200，`restored:true` | 软删除的才找得回来（真删的 404）；同场景已有同名 409 |

## 4. 本地回归（函数直跑 · 31 项）

增 → 改 → 查 → 删（软）→ 查（已消失）→ 恢复 → 查（又回来）→ 真删，全链路 + 各拒绝分支：

| 组 | 用例 | 结果 |
| --- | --- | --- |
| 体检 | `/api/health` **version 1.4.0** | ✅ |
| 增 | POST（201，id=90，char_count=5 服务端算） | ✅ |
| 改 | PATCH 只改寓意（名字没动）→ 词库读回新寓意 ✅；PATCH 改名字 → **char_count 重算** ✅ | ✅ |
| 改·拒绝 | 撞同场景名 409 / 空名字 400 / 空请求体 400 / 传不可改字段 400 / 超 20 字 400 / 编号非数字 400 / 不存在 404 | ✅ 7/7 |
| 删·确认锁 | 不带 confirm 400 / confirm 写错 400 / 不带编号 400 | ✅ 3/3 |
| 删·软 | DELETE → 200（mode=soft，recoverable=true）→ **GET 里该条消失（count 7→6）** → 再删/再改都 404 | ✅ 4/4 |
| 余力 | restore → 200 → **GET 里它又回来了** | ✅ 2/2 |
| 删·真 | `?mode=hard` → 200（recoverable=false）→ restore 404（真找不回来） | ✅ 2/2 |
| 老契约 | GET /names 405 / PUT 405 / POST /library 405 / 404 / scenes 6 场景 / 重复投稿 409 / library 200 | ✅ 7/8 |

> 那一项失败是**最后一条 `GET /api/library?scene=品牌` 超时**——单独复测 5 连发全部 200（首跑冷启 2.3s，之后 111–212ms），判定为**偶发网络抖动**，不是代码问题（公网复测该项也通过）。

## 5. 公网闭环（15/15 全过）+ 前端真实点击

公网地址上的同一条链路（实验数据：店铺 +「半盏灯」id=92，验证后已清理，库回 37 行）：

| 步骤 | 公网实测 |
| --- | --- |
| 体检 | `/api/health` → 200，**version 1.4.0**（新代码确实上线了） |
| 增 | POST「半盏灯」→ **201** id=92 |
| 改之前 | GET（keyword=半盏灯）→ count=1，寓意「留一盏灯，等晚归的人。」 |
| **改** | PATCH（只传 meaning）→ **200**，名字/字数原样没动 |
| 改之后 | 同一个 GET → 寓意「留一盏灯，给还在路上的人。」 |
| 删·锁 | 不带 confirm → **400**；confirm 写错 → **400**「确认值「写错了」和编号 92 的名字「半盏灯」不一致，没有删除」 |
| **删** | confirm 正确 → **200**，`mode:"soft"`、`recoverable:true`，回执带被删那条 |
| 删之后 | 场景列表 **count 7→6** 且无「半盏灯」；按名字查 → **`data: []`** |
| 软删除实证 | 直接查库：`id=92 半盏灯 is_deleted=true`——**行还在，只是被标记了** |
| 余力 | restore → 200 → GET 里**它又回来了**（count=1） |
| 真删 | `?mode=hard` → 200（recoverable=false）→ restore → **404**；收尾后 `names` 总数 **37** |

**前端（无头浏览器在公网词库页真实点击，控制台 0 报错）**：

| 动作 | 实测 |
| --- | --- |
| 进词库页（店铺） | 7 张卡，每张都有「复制 / 删除」两个按钮 |
| 第一次点「删除」 | 按钮变红「确认删除「前端演示行」？」；**Network 里 /names/ 请求数 = 0**；卡片还在 |
| 第二次点 | 真发请求；toast「已删除「前端演示行」· 数据仍保留在云端，可恢复」；列表 7→6，该行消失 |

> 一个新踩的坑，记下来：**浏览器里的 PATCH/DELETE 不是"简单请求"，会先发一趟 OPTIONS 预检**。
> 开工前先探了一发——网关的 CORS 层会**按请求的方法回显** `Access-Control-Allow-Methods: PATCH / DELETE`，放行 ✅，
> 所以前端可以直接用标准 REST 方法。实测预检也抓到了（第二次点击先 OPTIONS 再 DELETE）。

## 6. 已知边界（如实记，不许糊过去）

- **真删只作用于"活着的行"**：`?mode=hard` 对已经软删除的行会 404（要彻底清掉得先恢复再真删，或直接用 SQL）。这是有意留的保守设计——宁可多一步，也不给"一键抹掉所有痕迹"的入口；管理端批量清理排在后面
- 软删除的行会留在表里（`total` 里含 `is_deleted=true` 的行，页面数字只算活着的）——这正是"能找回"的代价
- 词库页只做了**删除**入口；「编辑」表单（PATCH 的前端入口）没做，PATCH 目前是纯接口能力（余力项）
