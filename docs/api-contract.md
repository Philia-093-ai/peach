# api-contract.md｜peach 接口契约（Day 18 版）

> 一句话：这份文档是**前后端之间的合同**。
> 合同签好了，前端和后端就能**各自独立干活**——前端按合同造假数据（mock），后端按合同写真逻辑，谁也不等谁，合起来还能一次对上。
>
> 比喻：装修时水电工和木工不天天开会。他们先约定好「插座在这个高度、孔径这么大」，然后各干各的。
> 这个约定就是接口契约；`/api/generate`、`/api/health`、`/api/scenes`、`/api/library`、`/api/names` 就是那几个插座。

- 版本：v1.2（Day 18：新增第一个**写入**接口 `POST /api/names`）
- 上游文档：`PRD.md`（验收标准 A1–A9）、`TECH_DESIGN.md`（技术路线）、`docs/day16-data-model.md`（两张表的字段）
- 今天状态：**`/api/health`、`/api/scenes`、`/api/library` 三个 GET 接口 + `POST /api/names` 一个写接口已部署并验证**；`/api/generate` 仍是"合同已签、后端待建"（第 4 周接真）
- 生效范围：Day 16–20 所有前后端联调都以本文件为准；改接口先改本文件再改代码

## 0. 通用约定（两个接口都遵守）

| 项 | 约定 | 为什么 |
| --- | --- | --- |
| 协议 | HTTPS | 公网部署自带；PRD A9 要求手机可访问 |
| 数据格式 | JSON，`Content-Type: application/json; charset=utf-8` | 中文必须带 charset，否则乱码 |
| 路径前缀 | `/api/` | 一眼区分「接口」和「静态页面」 |
| 成功/失败判别 | **看 HTTP 状态码 + body 里的 `ok` 字段**，两个都要看 | 只信状态码：某些网关出错会返回 200；只信 `ok`：无法区分是业务错还是服务器错 |
| 失败返回形状 | 永远是 `{ "ok": false, "error": "一句人话" }` | **绝不返回堆栈**（PRD A8 的硬要求） |
| 请求体上限 | 4 KB | 防超大数据，服务端已有兜底（超了返回 413） |
| 时间 | 服务端返回 UTC ISO 8601（如 `2026-10-10T13:05:16Z`） | 时区歧义最少 |

### 状态码清单（本项目的全部约定，不多不少）

| 码 | 含义 | 前端该怎么反应 | 算不算"失败" |
| --- | --- | --- | --- |
| 200 | 成功 | 正常渲染 | 否 |
| 201 | **创建成功**（Day 18 起，写接口用） | 当成功处理（`res.ok` 为 true），拿 `data.id` | 否 |
| 400 | 请求本身不对（关键词空 / 超 20 字 / JSON 格式坏 / 缺必填字段） | 提示 `error` 里那句话，**不重试**（重试也一样） | 是 |
| 404 | 路径不存在 | 说明白是地址错了 | 是 |
| 405 | 请求方法不对（对该路径用了 POST 之外的动词） | 属于前端 bug，开发期就该发现 | 是 |
| 409 | **冲突：要写的东西已经存在**（Day 18 起，重复提交） | 提示 `error` 里那句话，**不重试** | 是 |
| 413 | 请求体超过 4 KB | 提示内容太大 | 是（提示不重试） |
| 504 | 服务端处理超时（超过 10 秒，A3/A8） | 显示「生成超时，请重试」+ 重试按钮，**不扣额度** | 是（可重试） |
| 500 | 服务端内部出错 | 显示「生成失败，请重试」+ 重试按钮，**不扣额度** | 是（可重试） |

> 「可重试」和「不重试」的区别很重要：**400 重试一百次也一样失败**，让用户狂点是折磨；
> 504/500 是"这次不走运"，给重试按钮才有意义。这条区分写进契约，前端就不会做错。
>
> 409 特别说明：它不是"服务器坏了"，而是"你要的东西已经在那儿了"——**用户重新提交一百次也一样**，
> 所以属于"不重试"，和 400 一类。

## 1. 接口一：`GET /api/health`（今天已部署 ✅）

**作用**：体检接口。不带任何参数，回答一个问题——「这个服务还活着吗？活着的是什么版本？」
**为什么需要它**：部署到公网后，它是**第一个要确认的东西**（见第 3 节）。它通了，说明域名、证书、路由、函数运行时的整条链路都是通的。

### 请求

```http
GET /api/health HTTP/1.1
Host: <云函数公网域名>
```

无参数、无请求体、无需鉴权（MVP 不追求防刷）。

### 成功响应（200）

```json
{
  "ok": true,
  "service": "peach-health",
  "version": "1.0.0",
  "time": "2026-10-10T13:05:16Z",
  "runtime": "nodejs",
  "region": "ap-shanghai"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `ok` | boolean | 是 | 恒为 `true`（健康才返回 200） |
| `service` | string | 是 | 服务标识，固定 `"peach-health"`——将来日志里一眼认出是谁在答话 |
| `version` | string | 是 | 契约版本，跟着本文档的版本走 |
| `time` | string | 是 | 服务端当前时间（UTC ISO 8601）——**顺便验证服务器的表准不准** |
| `runtime` | string | 否 | 运行时标识（如 `nodejs`） |
| `region` | string | 否 | 部署地域（如 `ap-shanghai`）——排查"是不是部署到了别的区"时有用的线索 |

### 失败响应（500，极罕见）

```json
{ "ok": false, "error": "服务暂时不可用" }
```

> 实践中 `/api/health` 几乎不会 500——它什么都不依赖。**如果它挂了，基本是平台侧的问题（函数没部署上 / 配置错了）**，不是业务代码的问题。这正是它作为"第一道体检"的价值。

## 2. 接口二：`POST /api/generate`（合同已签，后端待建 ⚠️）

**作用**：peach 的主接口。收「场景 + 关键词」，回一批「名字 + 寓意」。
**今天的状态**：前端 `public/mock.js` 已按**完全相同的形状**造假数据在跑；Day 16–20 把后端接上、把 `MOCK_MODE` 改成 `false` 即可，**前端页面代码一行都不用动**——这就是先签契约再干活的回报。

### 请求

```http
POST /api/generate
Content-Type: application/json
```

```json
{ "scene": "品牌", "keyword": "海边咖啡店" }
```

| 字段 | 类型 | 必填 | 约束 | 校验在哪 |
| --- | --- | --- | --- | --- |
| `scene` | string | 否 | 取值：`品牌` / `店铺` / `宠物` / `网络昵称` / `作品` / `游戏角色`（与 scenes 表一致，以 `GET /api/scenes` 为准）；缺省按 `品牌` 处理 | 前端下拉已限定；服务端兜底 |
| `keyword` | string | 是 | 去空格后 1–20 个字（按**字符数**算，中文汉字算 1 个） | **前端先拦（A5/A6，不发请求）+ 服务端再拦** |

> 双保险的理由：前端拦住是**为用户省时间**（不用等一次往返），服务端拦住是**为数据兜底**（有人绕过页面直接调接口也不至于写坏数据）。

### 成功响应（200）

```json
{
  "ok": true,
  "scene": "品牌",
  "keyword": "海边咖啡店",
  "names": [
    { "name": "浪屿", "meaning": "想象一座海上小岛，安静得只听得见浪。" },
    { "name": "晨野", "meaning": "清晨的原野，一切刚刚开始的样子。" }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `ok` | boolean | 是 | 恒为 `true` |
| `scene` | string | 是 | **原样回显**请求里的场景——方便排查"前端传的和后端收到的是不是同一个" |
| `keyword` | string | 是 | **原样回显**请求里的关键词（已去空格） |
| `names` | array | 是 | 结果列表，**非空**（至少 1 条）；条数约定为 **6**（PRD A3） |
| `names[].name` | string | 是 | 名字本身，不含前后空格 |
| `names[].meaning` | string | 是 | 寓意/解释，**≤ 30 个字**（PRD A4；超长由服务端截断，不交给前端处理） |

### 失败响应

| 场景 | 状态码 | body |
| --- | --- | --- |
| 关键词为空 | 400 | `{ "ok": false, "error": "关键词不能为空" }` |
| 关键词超 20 字 | 400 | `{ "ok": false, "error": "关键词最多 20 个字" }` |
| 请求体不是合法 JSON | 400 | `{ "ok": false, "error": "请求格式不对，请刷新页面重试" }` |
| 请求体超 4 KB | 413 | `{ "ok": false, "error": "请求内容太大" }` |
| 生成超时（> 10 秒） | 504 | `{ "ok": false, "error": "生成超时，请重试" }` |
| 服务端生成失败 | 500 | `{ "ok": false, "error": "生成失败，请重试" }` |

### 前端契约（和上面一样重要）

后端守约还不够，**前端也得守约**，否则"合同"只签了一半：

| 约定 | 内容 | 出处 |
| --- | --- | --- |
| 校验 | 关键词空 / 超 20 字 → **不发请求**，本地就给提示 | PRD A5/A6 |
| 超时 | 10 秒没回 → 主动中断（`AbortController`） | PRD A3/A8 |
| 额度 | **只在成功时** `+1`；失败/超时**不扣** | PRD A7/A8 |
| 错误展示 | 只用 `error` 字段那句话；**绝不显示堆栈/英文报错** | PRD A8 |
| 渲染安全 | 一律 `textContent`，不拼 HTML | PRD A10 |

## 3. 接口三：`GET /api/scenes`（Day 17 已部署 ✅）

**作用**：把 Day 16 建的 `scenes` 表（场景字典）原样端出来。前端词库页的场景下拉框，选项就来自它。
**为什么单独一个接口**：场景是"字典"，名字是"正文"。字典很小、很少变，让前端先问字典再问正文，两边各司其职（就像先翻目录再翻正文）。

### 请求

```http
GET /api/scenes HTTP/1.1
```

无参数。

### 成功响应（200）

```json
{
  "ok": true,
  "count": 6,
  "data": [
    { "id": 1, "name": "品牌", "sort_order": 10 },
    { "id": 2, "name": "店铺", "sort_order": 20 }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `count` | number | 场景个数（= `data.length`） |
| `data[].id` | number | 场景编号——`names.scene_id` 关联的就是它（Day 16 定的那根线） |
| `data[].name` | string | 场景名（如 `品牌`） |
| `data[].sort_order` | number | 排序号，已按升序返回 |

## 4. 接口四：`GET /api/library`（Day 17 已部署 ✅ · 今天的主接口）

**作用**：读真库。按场景名查 `names` 表，回一批「名字 + 寓意」。**数据来自云数据库，不是前端写死的**——这就是 Day 17 要回答的问题：「页面上那份词库，凭什么相信它是真的？」

### 请求

```http
GET /api/library?scene=品牌&keyword=海&limit=6 HTTP/1.1
```

| 参数 | 类型 | 必填 | 约定 |
| --- | --- | --- | --- |
| `scene` | string | 否 | **场景名**（中文，如 `品牌`），不是编号；缺省按 `品牌`。填了不存在的场景 → 400，并在 `scenes` 字段里告诉你有哪些可选 |
| `keyword` | string | 否 | 名字或寓意里含这几个字就算命中；缺省不过滤 |
| `limit` | string | 否 | **返回条数上限（Day 17 余力加练）**。缺省 40，最大 100——上限必须有，否则 `?limit=999999` 会被人拿来拖垮服务 |

### 成功响应（200）

```json
{
  "ok": true,
  "scene": "品牌",
  "keyword": "",
  "count": 3,
  "total": 6,
  "limit": 3,
  "data": [
    { "id": 1, "name": "浪屿", "meaning": "想象一座海上小岛，安静得只听得见浪。", "char_count": 2 }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `scene` / `keyword` / `limit` | string/number | **原样回显**（limit 回显的是"夹过上限之后"的实际生效值） |
| `count` | number | 本次实际返回的条数（被 limit 截过） |
| `total` | number | 过滤后一共几条——`count < total` 就说明还有更多 |
| `data[].id` | number | 词条编号（names 表主键） |
| `data[].name` | string | 名字 |
| `data[].meaning` | string | 寓意（seed 里最长的 19 字，远低于 30 上限） |
| `data[].char_count` | number | 名字字数（生成器按"短名字优先"排序时要用） |

排序约定：短名字在前，同长度按 `id` 升序。
跨域约定：**CORS 由 CloudBase 网关统一处理**（函数里不写 `Access-Control-Allow-Origin`——两边都写会拼出 `origin,*` 这种非法值，浏览器直接拒绝，见 `docs/day17-verify.md` 的坑 3）。

### 失败响应

| 场景 | 状态码 | body |
| --- | --- | --- |
| 场景名不存在 | 400 | `{ "ok": false, "error": "没有「xx」这个场景", "scenes": ["品牌","店铺",...] }` |
| 数据库读失败 | 500 | `{ "ok": false, "error": "词库读取失败，请稍后重试" }` |
| 路径不存在 | 404 | `{ "ok": false, "error": "接口不存在" }` |

> 400 里带上可选场景列表，是让调用者"错也知道错在哪、下一步该怎么改"，而不是丢一句 500 了事。

## 5. 接口五：`POST /api/names`（Day 18 已部署 ✅ · 今天的主接口）

**作用**：往词库里**写**一个新名字（"投稿收录"）。读接口是"把库端出来"，写接口是"往库里放东西"——这是项目里**第一个会改数据库的接口**。
**今天要回答的问题**：**别人往我库里写东西，我怎么保证写进去的是干净的？** 答案分三层（见本节末尾）。

### 请求

```http
POST /api/names HTTP/1.1
Content-Type: application/json
```

```json
{ "scene": "品牌", "name": "云栖", "meaning": "云雾栖居之处，安静、有留白。" }
```

| 字段 | 类型 | 必填 | 约束 | 校验在哪 |
| --- | --- | --- | --- | --- |
| `scene` | string | **是** | 必须是 `scenes` 表里已有的场景名（如 `品牌`）；填了不存在的场景 → 400 | 服务端 |
| `name` | string | **是** | 去空格后 1–20 个字（按**字符数**算，中文汉字算 1 个） | 服务端 |
| `meaning` | string | 否 | 寓意；超过 30 个字由**服务端截断**（不报错，沿用 PRD A4 的约定）；缺省按空字符串处理 | 服务端 |

> 为什么 `name` 必填而 `meaning` 不必填？名字没了这件事就没意义；寓意缺了还能显示、超了截断就行——
> **能兜住的不为难用户，兜不住的才拒绝。**

### 成功响应（201 Created）

```json
{
  "ok": true,
  "data": {
    "id": 75,
    "scene": "品牌",
    "name": "云栖",
    "meaning": "云雾栖居之处，安静、有留白。",
    "char_count": 2,
    "created_at": "2026-10-11T14:12:33.000Z"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ok` | boolean | 恒为 `true` |
| `data.id` | number | **数据库新发的主键**——有它才证明"真的多了一行" |
| `data.scene` | string | 原样回显场景名（便于排查"前端传的和后端收到的是不是同一个"） |
| `data.name` | string | 去空格后**实际写入**的名字 |
| `data.meaning` | string | 实际写入的寓意（**已截断到 ≤30 字**） |
| `data.char_count` | number | **服务端算的**字数，不收前端传的值（前端算的不可信） |
| `data.created_at` | string | 数据库写入时间，已归一化为 UTC ISO 8601 |

> 成功用 **201** 而不是 200：REST 里 201 = "创建成功，资源已产生"。前端只认 `res.ok`（200–299 都算成功），不受影响。

### 失败响应

| 场景 | 状态码 | body |
| --- | --- | --- |
| 缺 `scene` | 400 | `{ "ok": false, "error": "缺少必填字段：scene（场景）" }` |
| 缺 `name` | 400 | `{ "ok": false, "error": "缺少必填字段：name（名字）" }` |
| 名字超 20 字 | 400 | `{ "ok": false, "error": "名字最多 20 个字" }` |
| 场景不存在 | 400 | `{ "ok": false, "error": "没有「xx」这个场景", "scenes": ["品牌","店铺", …] }` |
| **重复提交**（同场景同名） | 409 | `{ "ok": false, "error": "「品牌」场景下已经有「浪屿」这个名字了" }` |
| 请求体不是合法 JSON | 400 | `{ "ok": false, "error": "请求格式不对，请刷新页面重试" }` |
| 请求体超 4 KB | 413 | `{ "ok": false, "error": "请求内容太大" }` |
| 用 GET 访问这个地址 | 405 | `{ "ok": false, "error": "该地址只接受 POST 请求" }` |
| 数据库写失败 | 500 | `{ "ok": false, "error": "词条写入失败，请稍后重试" }` |

### 三层防线（今天要掌握的那句话）

| 层 | 防什么 | 靠什么 |
| --- | --- | --- |
| ① 格式层 | 缺必填、名字超长、JSON 坏、请求体太大 | 函数里的 `if` 判断 → 400 / 413，**一律回中文人话** |
| ② 关联层 | 场景名不存在（名字会挂空、变成孤儿数据） | 先查 `scenes` 表拿到 `scene_id`，查不到就拒绝 → 400 |
| ③ 数据层 | **重复提交**（同一场景下同一个名字写两遍） | **数据库唯一约束** `names_scene_name_key (scene_id, name)`（Day 16 建表时埋下的）→ 网关回 `DATABASE_23505` → 翻译成 409 中文 |

> **为什么重复要交给数据库拦，而不是在函数里先查一遍？**
> 因为"先查有没有、再插入"中间有一段时间差：两个请求同时进来，都会查到"没有"，然后都插进去，结果两条重复。
> 数据库的唯一约束是**原子**的——同一瞬间也只可能有一个成功。
> 这就是 Day 16 那条 `UNIQUE (scene_id, name)` 的价值：它不是"文档里写的一条规则"，
> 而是**最后一扇关得上、且关得死的门**。

## 6. 「公网地址第一次打开时，第一个想确认的是哪一件事？」

> 这是 Day 15 的问题。答案是：**先确认 `/api/health` 通不通。**

理由（打个比方）：公网部署是一栋新房子，链路很长——域名解析 → HTTPS 证书 → 平台网关 → 函数路由 → 运行时启动 → 代码执行。
这一长串里任何一环坏了，用户看到的都是同一句「打不开」。**如果一上来就去测最复杂的 `/api/generate`，坏了你根本不知道坏在哪一环。**

`/api/health` 是这条链路上**最轻、依赖最少**的一环：它不读数据库、不调外部 API、不需要参数。
所以它的通与不通，等于把问题一刀切成两半：

- **health 通了** → 域名、证书、网关、运行时全都是好的，剩下的问题一定在**业务逻辑内部**（能定位，范围小）；
- **health 不通** → 问题在**平台配置层**（部署/re路由/域名），跟业务代码一点关系都没有，先别改代码，去查配置。

**这就是"体检接口"的价值：用最小的一次请求，把一大片不确定性砍掉一半。**
（同样的思路：修电脑先看电源灯亮不亮，而不是直接重装系统。）

## 7. 契约冻结与变更规则

| 规则 | 内容 |
| --- | --- |
| 谁先改 | **先改本文件，再改代码**——避免"代码是新形状、文档是旧形状"的假契约 |
| 改了什么要记 | 在下面「变更记录」追加一行，写清日期、接口、改了什么、为什么 |
