>
> **采集方式说明（重要）**：今日计划的板块①是「邀请第三方真人试用」。本次**未执行真人试用**，原因与限制见文末「§6 采集方式的局限」。下面所有结论均来自**我直接调用线上接口 + 核对仓库源码**得到的可复现证据，不依赖任何浏览器环境，因此不受本机代理等测量噪声影响。

## §2 F-27-1 证据链

### 2.1 后端返回 6 个场景（原始响应）

请求：

```
GET https://apple-1-d2g1zk4836ce03980-1503730028.ap-shanghai.app.tcloudbase.com/api/scenes
```

响应（HTTP 200，实测 782 ms）：

```json
{"ok":true,"count":6,"data":[
  {"id":1,"name":"品牌","sort_order":10},
  {"id":2,"name":"店铺","sort_order":20},
  {"id":3,"name":"宠物","sort_order":30},
  {"id":4,"name":"网络昵称","sort_order":40},
  {"id":5,"name":"作品","sort_order":50},
  {"id":6,"name":"游戏角色","sort_order":60}
]}
```

**`count` 是 6**，且带 `sort_order` 排序字段，说明后端认真维护了 6 个场景。

### 2.2 六个场景各自的名字条数（逐个查证）

请求 `GET /api/library?scene=<场景>&limit=100`：

| 场景 | 条数 | 名字 |
|---|---|---|
| 品牌 | 7 | 浪屿、晨野、拾光、云栖、白鹿纪、野柿子、南风集 |
| 店铺 | 6 | 苔痕、灯下人、慢半拍、半山书角、一勺晚风、口袋月光 |
| 宠物 | 6 | 汤圆、煤球、布丁、来福、雪碧、年糕 |
| 网络昵称 | 6 | 困困兽、熬夜冠军、一半海水、柠檬气泡、慢速飞船、脆皮打工人 |
| **作品** | **6** | **山海拾遗、长夜微光、折纸纪年、潮汐来信、候鸟南飞、星野笔记** |
| **游戏角色** | **6** | **拾七、霜刃、云中君、雪满弓、山鬼谣、白露未晞** |

合计 37 条名字，其中 **「作品」6 条 + 「游戏角色」6 条 = 12 条**，是本次问题影响的数据。

### 2.3 前端下拉写死 4 个（源码原文）

`public/index.html` 生成器下拉（第 43–48 行）：

```html
<select id="scene">
  <option value="品牌" selected>品牌</option>
  <option value="店铺">店铺</option>
  <option value="宠物">宠物</option>
  <option value="网络昵称">网络昵称</option>
</select>
```

`public/index.html` 词库页下拉（第 108–113 行）：

```html
<select id="lib-scene">
  <option value="品牌" selected>品牌</option>
  <option value="店铺">店铺</option>
  <option value="宠物">宠物</option>
  <option value="网络昵称">网络昵称</option>
</select>
```

两处都是**硬编码的 4 个 option**，没有任何从 `/api/scenes` 动态渲染的逻辑。

### 2.4 离线样本也缺同样两类（F-27-3）

`public/mock.js` 第 60 行的 `MOCK_BATCHES` 只有 4 个键：`品牌 / 店铺 / 宠物 / 网络昵称`。
第 105 行、152 行取不到场景时分别回退到 `MOCK_BATCHES['品牌']` 或空数组 —— 意味着这两个场景即使在离线模式下也无法得到结果。

### 2.5 用户视角的后果

一位真实用户打开站点，如果他这次想给**作品**（小说 / 专辑 / 画集）或**游戏角色**起名：

- 下拉框里**根本没有这个选项**，他只能从 4 个里硬挑一个不相关的
- 结果就是：他拿到的名字与他的真实需求不匹配 → **右上角的「数据来自云数据库」这些名字其实早就准备好了，却永远送不到他手上**

这不是「功能缺失」，而是**已经做好的东西没接上**——修复成本极低，用户收益明确。

## §3 为什么它是「最高优先级」

对照今日的约束（**不许按反馈大改、不许加新功能**），这条问题同时满足三个条件：

1. **有确凿证据**：接口原始响应 + 源码原文 + 逐场景条数，全部可复现，不依赖任何主观判断。
2. **修复成本极低**：只是在两个 `<select>` 里补两个 `<option>`，不改任何 JS 逻辑、不改接口、不改数据结构。属于「接上已有能力」而非「造新能力」。
3. **用户收益直接**：解锁 12 条已入库数据，让 6 个场景全部可用。

反过来，被我**主动排除**的候选（F-27-2 加载慢）恰恰是反面教材：它在我的测量环境里看着很严重，但独立验证表明是**本机代理造成的假象**（见 §5）。如果拿它当最高优先级去「优化性能」，就会误判方向、做出无用的改动 —— 这正是今日禁止的「按反馈大改」。

## §5 观察项 F-27-2 的排除过程（为什么判定为本机噪声）

初次用全新浏览器档案（headless Edge + CDP）访问站点，测得首屏加载 **41.9 秒 / 81.8 秒**（两次）。

为判断这是站点问题还是测量环境问题，改用 **Python 直接 HTTP 请求**逐个下载同一批静态文件：

| 文件 | 大小 | 耗时 |
|---|---|---|
| `/`（首页） | 8,943 B | 617 ms |
| `/index.html` | 8,943 B | 370 ms |
| `/style.css` | 16,583 B | 417 ms |
| `/app.js` | 11,837 B | 464 ms |
| `/mock.js` | 13,472 B | 404 ms |
| `/library.js` | 8,515 B | 437 ms |
| `/live.js` | 8,913 B | 428 ms |
| `/router.js` | 3,059 B | 368 ms |
| `/card.js` | 2,389 B | 368 ms |
| `/filter.js` | 3,578 B | 362 ms |

**全部资源合计约 4.3 秒下载完毕，单个最大 617 ms。**

结论：站点本身的分发速度正常（静态托管 + CDN）。headless 浏览器里 40–80 秒的差异来自**本机开着 WattToolkit 系统代理**，浏览器走代理通道时被显著拖慢。**真实用户不带我们的本机代理，不会遇到这个问题**。因此不作为修复项，仅记录为测量环境注意事项。

## §6 采集方式的局限（如实标注）

今日计划要求「**一位没参与项目的真人**在**自己的设备**上完成核心流程」。本次**未达成**这一项，实际情况是：

- 尝试用「全新浏览器档案」模拟第三方视角，但被本机环境的两个障碍卡住：
  1. 本机代理导致 headless 浏览器加载 40–80 秒，测量结果不可信（§5）
  2. headless 环境下 `Runtime.enable` / `Network.enable` 等 CDP 域命令在页面加载期间间歇性挂起，无法稳定读取页面内容
- 在与用户确认后，改为**使用已确凿核实的问题（F-27-1）**作为最高优先级修复对象。该问题通过接口与源码双向核对得到，证据强度高于一次真人试用的口头反馈，但**它替代不了「真人视角」这一项**。

**遗留待办**：真人第三方试用仍未执行。建议在下一次有真实用户可用时补做，重点观察：
- 用户是否能独立看懂「场景」这个概念的用法
- 用户是否会疑惑「为什么只有这 4 类」
- 用户拿到名字后是否知道怎么复制
