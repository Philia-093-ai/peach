# rollback-playbook｜peach 回滚手册（Day 26 建立）

> 一句话：**出事的时候没有时间想，所以现在想。**
> 这本手册在演练里实测过一遍：坏版本上线 → 10.5 秒退回 v1.0（记录见 `docs/day26-verify.md`）。

## 0. 先记住一个事实：静态托管没有"版本管理"

`tcb hosting deploy` 的官方说明原文：**"file upload only, no build, no version management"**
（CLI 还会提示：需要版本管理请用 `tcb app deploy`）。

所以别指望"点一个按钮退回上一版"。peach 的回退路径是：

```
回退 = 用历史产物重新部署
     = git 里永远有一份每个版本的原样产物（public/）
     + hosting deploy public 把它重新推上线
```

这就是为什么「确认可回退历史」是发布日的前置项：**git 提交就是我们的版本库**。

## 1. 静态托管回退（本手册的主路径，已演练 ✅）

```bash
# ① 找到要退回的版本（一般就是上一个 tag 或上一个提交）
git log --oneline -5
git tag -l

# ② 生成回退提交（推荐 revert：历史里留下"退过"的记录，而不是假装没发生过）
git revert --no-edit <事故提交sha>
git commit --amend -F <中文提交信息>        # 可选：换成规范中文信息

# ③ 重新部署（4~8 秒）
tcb hosting deploy public -e <环境ID> --verify

# ④ 公网确认（三条都要看）
#    a. 页面引用还原（坏文件名消失）
#    b. 逐文件 md5 与本地一致
#    c. 真点一次核心功能（只看"页面能打开"不够——事故坏的往往就是 JS）
```

**实测耗时（2026-10-14）**：revert 提交 1.8 秒 + 重新部署 7.8 秒 + 公网校验 0.7 秒 = **10.5 秒**。

### ⚠️ 这条路上已经踩过的一个坑

`core.autocrlf=true` 时，`git checkout/revert/archive` 会把文件写成 **CRLF**，
而线上一直是 **LF**（本机工作区文件都是 LF）。回退后若直接对比 md5 会出现"明明内容一样却对不上"。
**规避**：回退后部署前，把 `public/` 里被改写的文件统一回 LF
（读入 → `b.replace(b'\r\n', b'\n')` → 写回），再部署、再核对。

## 2. 云函数回退（备查，今天没实操）

云函数有**版本/别名**概念，但本项目一直用 `fn deploy api --force` 直接覆盖 `LATEST`。
回退办法（按成本从低到高）：

1. **重新部署旧代码**：`git checkout <好版本> -- cloudfunctions/ && tcb fn deploy api --force`
   —— 和静态托管同思路，最熟、最稳；
2. 云函数控制台回退版本（需要登录态，本机 CLI 拿不到浏览器登录态，脚本做不了）；
3. 注意：函数回退后 **`/api/health` 的 version 会跟着回去**，前端不受影响（接口形状没变才能这么退）。

## 3. 数据恢复（备查，今天没实操）

- 写接口**默认软删除**（`is_deleted` 标记 + `deleted_at`），数据没真删：
  `POST /api/names/:id/restore` 就能找回；
- 真删（`mode=hard`）过的行：靠 PostgreSQL 的备份/快照（CloudBase 控制台），
  CLI 侧没有现成命令 —— 所以**约定：hard 删除只对确认不要的数据用**；
- 数据库日常兜底：`db/seed.sql` 里存着 36 条种子名字，最坏情况能重建词库骨架。

## 4. 什么情况必须回滚？（判断表 · 余力加练）

> 回滚不是失败，是止损。判断核心只有一个问题：**留着它，用户会不会继续受损？**

| # | 症状 | 必须回滚？ | 理由 / 先做什么 |
| --- | --- | --- | --- |
| 1 | 密钥泄露（任何形式） | **必须，立刻** | 唯一"时间越久损失越大"的问题；先**作废密钥**再回滚，顺序不能反 |
| 2 | 核心功能坏了（生成/词库打不开、点击无反应） | **必须** | 用户拿着一个废站；修复时长 > 回滚时长就先退 |
| 3 | 数据在写坏（写接口把脏数据入库） | **必须** | 每一分钟都在扩大污染面；先停写入再谈修复 |
| 4 | 安全/合规问题（页面被注入、跳转到陌生域） | **必须** | 同 1，先止损再排查 |
| 5 | 展示类小错（错别字、样式歪了、文案不当） | 不回滚 | 修复 < 回滚 + 再发布的成本；正常发下一版 |
| 6 | 个别用户反馈异常、复现不了 | 先观察 | 加日志、复现；没有证据不动线上 |
| 7 | 性能变慢但功能正常 | 视情况 | 有明确劣化曲线（如超时率）→ 退；只是"感觉慢"→ 观察 |
| 8 | 修复时间明确 > 10 分钟且影响面是全量用户 | **建议回滚** | 回滚只要 10.5 秒（实测）；先恢复，再慢慢修 |
| 9 | 修复时间明确 < 回滚 + 验证的成本 | 不回滚 | 比如一行文案 1 分钟能改完 |
| 10 | 不确定坏没坏 | 先取证再决定 | 用发布前检查 + F12 + 接口探针确认；**不靠感觉回滚** |

**一句话判据**：影响面 × 恢复时长。全量用户 + 核心功能 + 修复要几分钟以上 → 回滚；
零星 + 展示层 + 一分钟内能修 → 直接修。

## 5. 回滚前的三个动作（别跳过）

1. **留下事故现场**：截图 / 保存报错原文 / 记下发现的时刻（复盘要用，也是今天的作业）；
2. **确认退到哪**：上一个 tag（`v1.0`）或上一个已验证的提交，**不要凭感觉选 sha**；
3. **备份当前状态**：坏版本也是证据，`git revert` 留痕而不是删历史。
