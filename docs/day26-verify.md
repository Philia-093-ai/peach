## ⑤ 计划外事故：本地 .git 受损（如实记录）

**发生了什么**：发布与演练的 4 个提交（`ebf8b97` 发布 v1.0、`bff2d64` P0 修复、`dd91ec4` 事故、`43ff156` 回滚）做完之后，一次本地 rebase 操作途中进程被杀，随后发现 `.git` 大量内容丢失：`refs/` 目录整个消失、24 个提交对象仅剩 2 个可用（Day 8/9），Day 10 起的提交对象全部丢失。

**损失评估**：
- 工作区文件 **零损失**（全部内容完好，含 Day 23–26 的所有代码、文档、截图）✅
- GitHub 远程 **零损失**（Day 1–22 完整历史都在，远程 main = `632ce0d`）✅
- 丢失的只是"本地对象库"，可从远程重建

**做了什么（按顺序）**：
1. **第一时间全量备份**整个 peach 目录（169 个文件 / 13 MB）→ `_backup_peach_20261014_git受损前/`
2. 重建 `refs/` 目录、把 main 指回 reflog 最后位置 → 确认对象缺失范围（`git fsck`）
3. 尝试 `git clone` 从 GitHub 恢复 → **被代理挡住**（github.com 通道 502/超时，与 Day 23–25 的推送失败同源）
4. 写好一键恢复脚本 `_d26_recover.py`：克隆 → 换上新的 `.git`（受损原件保留为 `.git-broken-20261014` 备查）→ 把工作区当前内容（Day 23–26 全部改动）作为一次"重建提交"入库 → 打 tag `v1.0` → 推送
5. 本日不依赖 git 的交付物（三张截图、本文件、回滚手册）全部完成并落在工作区

**教训（正是今天主题的镜像）**：
- **回滚演练练的是"出事怎么办"，结果自己先遇上了真事故** —— 手册第 5 节"回滚前三个动作"（留现场 / 确认退到哪 / 先备份）一个都没跳过，所以零损失
- 危险 git 操作（rebase/amend）之前应该先 `git bundle` 或整目录备份 —— 这次是备份救了 Day 23–26 四天的活
- **备份要放仓库外面**：`.git` 受损时，同仓库内的任何"备份"都一起陪葬
