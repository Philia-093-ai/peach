## 1. 为什么是「两张表」，不是一张

一个特别自然的疑问：名字不就是「场景 + 名字 + 寓意」吗，一张表全塞进去不行吗？

可以，但会立刻撞上两个麻烦：

| 如果只有一张表 | 会怎样 |
| --- | --- |
| 场景名在每个名字里重复写一遍 | 「品牌」这两个字要写 6 遍、10 遍……改一个字的写法就得改一大片（数据冗余） |
| 想改场景的排序 / 显示名 | 得 UPDATE 一整片行，而且容易改漏，出现「品牌」和「品牌 」两个版本 |

**两张表的分工**，用一个生活比喻就清楚了：

> `scenes` 是一本**字典**（只有几个词条，每个场景一条，写得准）；
> `names` 是一本**名录**（很多条，每条只记「我叫什么、我属哪个场景」）。
> 名录里不重复抄整页字典，只抄一个**编号**——这个编号就是连接两本册子的那根线。

这就是数据库里最经典的「**主表 + 字典表（外键关联）**」结构。

## 2. 两张表分别存什么

### 表 1：`scenes` —— 场景字典表

一行 = 一个命名场景。数据量小（今天就 6 行），但它是「场景」这件事的**唯一权威来源**。

| 字段 | 类型 | 约束 | 存什么 |
| --- | --- | --- | --- |
| `id` | `integer` | 主键 | 场景编号，**人工指定**的稳定数字（1、2、3……） |
| `name` | `text` | 非空、唯一 | 场景名（「品牌」「店铺」…），直接给界面显示 |
| `sort_order` | `smallint` | 非空、默认 0 | 排序权重，数字小的排前面，决定下拉框顺序 |
| `created_at` | `timestamptz` | 非空、默认 `now()` | 创建时间 |

### 表 2：`names` —— 名字词条表

一行 = 词库里的一个名字。这是**会长大的那张表**（今天是 32 行，以后会越来越多）。

| 字段 | 类型 | 约束 | 存什么 |
| --- | --- | --- | --- |
| `id` | `serial` | 主键（自增） | 词条编号，数据库自动发号 |
| `scene_id` | `integer` | 非空、**外键 → `scenes.id`** | **← 关联字段**：这个名字属于哪个场景 |
| `name` | `text` | 非空 | 名字本身（如「浪屿」） |
| `meaning` | `text` | 非空 | 一句话寓意（≤30 字，PRD A4） |
| `char_count` | `smallint` | 非空 | 名字的字数，给词库「按字数筛选」用（Day 12 的按钮） |
| `created_at` | `timestamptz` | 非空、默认 `now()` | 创建时间 |

外加一条**联合唯一约束**：`UNIQUE (scene_id, name)` —— 同一个场景里，同名名字只能有一条。
它顺便干了两件好事：① 防止词库重复收录；② 让种子脚本能写成「重复执行不报错」（见第 5 节）。

## 3. 它们靠哪个字段关联

**靠 `names.scene_id` → `scenes.id`。**

```
   scenes（字典：6 行）                  names（名录：32 行）
 ┌────┬──────────┐                ┌────┬──────────┬────────┬────────────┐
 │ id │   name   │                │ id │ scene_id │  name  │  meaning   │
 ├────┼──────────┤                ├────┼──────────┼────────┼────────────┤
 │  1 │  品牌    │◄───────────────│  1 │    1     │  浪屿  │ 想象一座…  │
 │  2 │  店铺    │◄──────────┐    │  2 │    1     │  晨野  │ 清晨的原野…│
 │  3 │  宠物    │           └────│  7 │    2     │ 半山书角│ 开在半山腰…│
 │  4 │ 网络昵称 │                │ 13 │    3     │  汤圆  │ 白白软软…  │
 │  5 │  作品    │                │ 19 │    4     │熬夜冠军│ 自嘲式幽默…│
 │  6 │ 游戏角色 │                │ 25 │    5     │山海拾遗│ 从山海经里…│
 └────┴──────────┘                └────┴──────────┴────────┴────────────┘
                                          │
                                    每行的 scene_id
                                    指向 scenes 的 id
```

- 数据库层面：`scene_id` 上有一个 **外键约束**（`REFERENCES scenes(id)`），
  意味着**插入一个不存在的场景编号会被数据库直接拒绝** —— 它替我们守住了「名字必须属于真实存在的场景」这条规则。
- 查询层面：想看「品牌」下所有名字，就是一次 **JOIN**：

  ```sql
  SELECT s.name AS scene, n.name, n.meaning
  FROM names n
  JOIN scenes s ON n.scene_id = s.id     -- ← 就是这根线
  WHERE s.name = '品牌'
  ORDER BY n.char_count, n.name;
  ```

  这根线另一端连着**今天的 select 验证**和**Day 17 的读接口**。

> 为什么不用「场景名」当关联字段？因为名字可能改（「网络昵称」将来想改成「网名」），
> 而**编号不会变**。用不会变的东西做连接，改起来才不会牵一发动全身。

## 4. 每个字段的类型，为什么这么选（余力加练）

| 字段 | 选了 | 为什么不选别的 |
| --- | --- | --- |
| `scenes.id` | `integer`（人工指定） | 字典表的编号应该**跨环境一致**——本地、开发、线上都用 1=品牌。如果让它自增，换个环境顺序一乱，seed 和前端就全对不上了。用固定整数最稳。 |
| `names.id` | `serial`（自增整数） | 词条数量会长大，且我们**不关心它的具体值**，只要求唯一。交给数据库自动发号最省心。用 `integer` 而不是 `bigint`：21 亿条足够，还省一半空间。 |
| `scene_id` | `integer` | **外键两端类型必须一致**（`scenes.id` 是 `integer`）。类型不一致会造成隐式转换、索引失效，甚至建不出外键。 |
| `name` / `meaning` | `text` | PostgreSQL 里 `text` **没有长度上限**，且性能与 `varchar(n)` 完全相同。长度限制交给**业务规则**（寓意 ≤30 字）去管，不必写死在类型上——否则以后想把 30 改 40 就要改表结构。 |
| `char_count` | `smallint` | 名字最多 20 个字，`smallint`（±32767）绰绰有余；比 `integer` 省一半空间。**用刚好够用的最小类型**，是省钱省 I/O 的好习惯。 |
| `created_at` | `timestamptz` | **带时区**的时间戳。数据库内部统一按 UTC 存，显示时再按用户时区换算——从根上避免「这个 10 点是北京时间还是 UTC」的扯皮。**别用 `timestamp`（不带时区）**。 |
| `sort_order` | `smallint` | 排序权重，几十几百的级别，`smallint` 够用。 |

**一句话心法**：类型选择不是「越大越保险」，而是**「刚好装得下、且不给以后添麻烦」**。

## 5. 和已有东西的对应关系

| 数据模型里的 | 对应今天的哪个东西 |
| --- | --- |
| `scenes.name` 的 6 个值 | PRD 的下拉场景（品牌/店铺/宠物/网络昵称）**+ 2 个新增**：`作品`、`游戏角色` |
| `names` 里的 24 条 | 与 `public/mock.js` 的假数据**同名同寓意**（方便对照） |
| `names` 另外 8 条 | 给新增的 `作品` / `游戏角色` 两个场景配的名字 |
| `names.char_count` | Day 12 结果区「2字 / 3字 / 4字」筛选按钮依赖的字段 |
| `names.scene_id` + `scenes.id` 的 JOIN | Day 13 词库视图「按场景 + 关键词」查询的数据来源；Day 17 读接口就建在它上面 |

> **关于新增的 2 个场景**：PRD 只写了 4 个场景，那是**前端下拉当前开放的**范围。
> 数据库作为数据的权威来源，多存 2 个常用场景（`作品`＝小说/专栏名，`游戏角色`＝角色名），
> 好处是**数据和界面解耦**——以后想在前端加场景，改一行数据即可，不用动表结构。
> 今天**不动前端**，所以页面上仍然只显示 4 个场景，这是预期行为。
