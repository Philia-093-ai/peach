# filter-check · 筛选交互自检

> 一句话：**它是筛选功能的"验收清单"**——把"筛选必须做到的几件事"固定下来，
> 每次动筛选相关代码，照着走一遍，不漏两端（空结果、清空恢复）。

## 为什么需要它

筛选是「用户缩小范围」的动作，写的人容易只盯着主路径，漏掉两端：

- 挑到空结果 → 用户以为页面坏了；
- 清空后回不到原样 → 用户以为数据丢了。

这两端都不难做，但很容易忘。所以把它们写成清单，每次照做。

## 什么时候用它

- 结果区新增 / 修改筛选（chips、下拉、标签切换、搜索框）
- 有人反馈「筛选后没反应 / 结果没了 / 回不去」
- 筛选功能上线前（自检 + 留痕）

## 动手前先读什么

1. `public/app.js` —— 搞清楚当前这批数据存在哪个变量里（筛选只改「显示」，不改数据源）
2. `public/card.js` —— 卡片怎么渲染的，复用 `renderNameList`
3. `public/style.css` 顶部两条组件约束：文字对比度 ≥ 4.5:1（小字）、竖向间距只用 8 的倍数

## 硬规则（缺一条就是没做完）

1. **数据源不动**：筛选只过滤「要显示的那几个」，原始批次原样留着——清空才能恢复。
2. **三种情况都要有明确画面**
   - 有结果：只显示命中的卡片，并写清「显示几个 / 共几个」
   - 无结果：给一条说人话的空状态（写清"这次没有 X"，不许白屏），**筛选控件不许跟着消失**，并给「看全部」出口
   - 清空恢复：点「全部」回到完整原批次，卡片数量与初始一致
3. **当前选中项看得见**：选中项有明确视觉差（底色 + 描边 + 字重），并写 `aria-pressed="true"`；未选中写 `false`。
4. **结果数量用文字说**：只靠卡片数量变化不算反馈；计数文字挂 `role="status"` + `aria-live="polite"`，读屏会播报。
5. **筛选控件只在有数据时出现**：初始空状态、生成中（骨架屏）、错误状态都隐藏，免得用户对着一批不存在的卡片筛。
6. **筛选与生成互不干扰**：重新生成 → 筛选自动回到「全部」（新的一批，旧条件不该残留）。
7. **点击筛选不丢焦点**：不要每次重建整排按钮（重建会把键盘焦点扔回页面顶部）；只更新状态。重建时要把焦点送回对应按钮。

## 无障碍加练清单

8. **控件语义**：用 `<button type="button">`，不要 `<div onclick>`；容器 `role="group"` + `aria-label`。
9. **键盘可达**：Tab 能走到每个按钮，焦点有可见光圈（复用 `:focus-visible` 那套光圈）。
10. **触控目标够大**：按钮高度 ≥ 36px、左右内边距 ≥ 12px（手指点得中）。
11. **颜色不单独承载信息**：选中态除颜色外，还有 `aria-pressed` + 字重/边框差异（色弱、色盲用户也能分辨）。

## 自检怎么跑

改完按上面 1–11 逐条核对。能自动化的用 CDP 脚本跑（真实鼠标点击，别用 `.click()`），断言：

- 卡片数量（筛选前 / 筛选后 / 清空后）
- 计数文案、`aria-pressed` 取值
- 无结果状态文案 + 出口按钮在不在
- `focus` 有没有留在被点的按钮上
- 全程 console 零报错

## 留痕（每次调用都要写）

在 `docs/day12-skill-log.md` 追加一条，格式固定：

```
## 调用 N · YYYY-MM-DD HH:MM · 目的
- 逐条：1 PASS / 2 PASS / … / 11 PASS（FAIL 写清现象和怎么修的）
- 结论：能不能交
```

## 常见坑（踩过就记下来）

- 用 `innerHTML` 拼卡片 → 一律 `textContent`（Day 7 的 A10 老规矩）
- 筛选后忘了同步 `aria-pressed` → 读屏听到的状态和眼睛看到的不一样
- 无结果时把筛选条一起清掉 → 用户被锁在空页面里出不来
- 数中文字数用 `str.length` → 遇到表情符号会数错；本项目名字都是中文，`split('')` 足够，但知道有这个坑
